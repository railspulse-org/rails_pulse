# The dashboard displays every time in the host's `config.time_zone`, the zone summaries are bucketed in, and says so

`SummaryJob` cuts day, week and month buckets in `Time.zone`, which in a job process is the host's `config.time_zone`. The dashboard formats every axis label, tooltip, timestamp column and breadcrumb in that same zone: Ruby formats the `Time.zone`-aware values ActiveRecord returns, and the chart controller receives the zone's IANA name and formats through `Intl.DateTimeFormat` with it. A badge next to every chart names the zone (`TimeRange.aggregation_zone_short_label`, with the full name and the resolved window in its title), chart tooltips end with it, and the custom range picker states it, because a daily point is meaningless without knowing which midnight it starts at.

Formatting in the browser's zone was rejected. It is what the charts did before, and it put a summary for September 22 00:00 UTC under September 21 for anyone west of UTC. Daily totals and percentiles are fixed at write time; relabelling them in another zone would imply local-day values that were never computed. The server's OS zone (`getlocal`) was rejected for the same reason: it is whatever the container happens to run in and has no relationship to the bucket boundaries.

A viewer-selectable zone was rejected for now. Hourly rows could be re-bucketed, but daily, weekly and monthly summaries cannot without recomputing them, so a selector would either lie for those periods or only apply to some charts. If one is added, it must recompute rather than relabel.

The one assumption: the dashboard request's `Time.zone` is the zone the job ran under. That holds when both are `config.time_zone`. A host that sets `Time.zone` per user in middleware wrapping the engine's controllers would see a badge naming the display zone while the daily buckets stay in the job's zone; `TimeRange.aggregation_zone_label` documents this and the fix is to leave the engine's requests on the configured zone.
