# Applications that cannot share a database can share one Rails Pulse: they send to a central the operator runs, which keeps each in a database of its own

_Recorded 2026-11._

Rails Pulse keeps what it collects in the host's own database (decision 0006), which assumes that every process that writes or reads it can reach that database. Applications that run on SQLite in containers of their own, each with a volume no other container can mount, cannot share a dashboard that way: each has its own, and none can see the others'.

Two optional modes, off unless configured, cover them. In remote mode an application keeps no Rails Pulse tables. Collection is unchanged; at the hand-off the writer's queue carries items for a central instead of rows, and the writer thread posts each batch it drains, gzipped JSON over HTTPS, authenticated by a token the central gave that application. Everything that becomes a row locally travels: requests and their operations, job runs, exceptions (read off the exception and redacted with the application's own filters before they leave), the writer heartbeat, deploy markers. Sending keeps the writer's guarantees (decision 0005): nothing happens on a request or job thread, a full queue drops the newest item, a failing central costs one short timeout per backoff and is held for a bounded retry, and nothing is raised to the host. In central mode a Rails app the operator runs with the same gem receives the batches, finds the application by its token, and records each item in that application's database with the code that would have recorded it locally, so a request, a job run or an exception means the same thing on either side.

This keeps the premise of decision 0006. The central is the operator's own application on the operator's own infrastructure, not a vendor's service: the data moves between two of the operator's processes as it would to a database server they run, under the same compliance rules. It is also why the modes do not use the Cloud sync contract (decision 0021). That contract is written for a third party, so it sends only what comes from code, as summaries keyed by content; a central is where the detail lives, so it receives what a local install would store, SQL as it ran included (normalised and fingerprinted there, and stored only with the central's own `capture_actual_sql`). Cloud works with neither mode, since it syncs from tables a remote application no longer has. With neither configured, nothing here runs and no network call is made.

Each application is a shard of `RailsPulse::ApplicationRecord`. Outside an application's context the class is connected to an empty in-memory database, so a query fails instead of landing in whichever application is configured first, while models still load, as an eager-loading boot needs. The process caches that hold one database's ids or answers (rollups, the route cache, the schema check, the deploy SHA) are kept per application. The dashboard is the same engine (decision 0010), mounted once under a path segment naming the application; the segment picks the shard and becomes the prefix every link is generated under. Summaries, cleanup and the schema check run per application, and the tasks that prepare databases load the schema into each application's.

We rejected sending summaries only, as Cloud does: the dashboard is built on raw requests, operations and occurrences, and a central with only summaries would be a second, smaller product. We rejected a shared database server: these applications run on SQLite by choice, and putting their monitoring on a server they do not otherwise need inverts the premise of decision 0006. We rejected one database for every application with an application column: every model, query, index and unique constraint would need it, and a missed one mixes applications' data; shards keep the gem's tables and code as they are.

The costs: detail now leaves each application, SQL values included, so the central must be run with the trust a database would be. Delivery is at least once, made idempotent per batch by `batch_id`, and held batches live in the sending process's memory, so a long outage or a restart loses data. Settings that shape storage and the dashboard (thresholds, tags, retention, time zone) are the central's, for every application. Features that need the monitored application's own router or tables on the central (route backfill, EXPLAIN) do not work there.
