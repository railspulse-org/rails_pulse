# Several applications can share one Rails Pulse: remote applications send, a central keeps each in a database of its own

_Recorded 2026-11, for the virtual360-io fork._

Rails Pulse keeps its data in the host's database (decision 0006), which assumes every process that writes or reads it can reach that database. Applications that run on SQLite in containers of their own, each with a volume no other container can mount, cannot have one dashboard for all of them that way. So the fork adds two modes, off by default and each a configuration of its own.

In remote mode the application keeps no Rails Pulse tables. Collection is unchanged; at the hand-off the writer's queue carries items for a central instead of rows, and the writer thread posts each batch it drains, gzipped JSON over HTTPS, authenticated by a token the central gave this application. Everything that becomes a row locally travels: requests and their operations, job runs, exceptions (read off the exception and redacted with this host's filters before they leave), the writer heartbeat, deploy markers. Sending keeps the writer's guarantees (decision 0005): nothing happens on a request or job thread, a full queue drops the newest item, a failing central costs one short timeout per backoff and is held for a bounded retry, and nothing is raised to the host. The central receives the batches, finds the application by its token, and records each item in that application's database with the code that would have recorded it locally, so a request, a job run or an exception means the same thing on either side.

Each application is a shard of `RailsPulse::ApplicationRecord` with no default shard: a query outside an application's context raises instead of landing in whichever application is configured first, and the caches that hold one database's ids are kept per application. The dashboard is the same engine (decision 0010), mounted once under a path segment naming the application; the segment picks the shard and becomes the prefix every link is generated under. Summaries, cleanup and the schema check run per application.

We rejected sending summaries only, as the Cloud client does (decision 0021): the dashboard is built on raw requests, operations and occurrences, and a central that only had summaries would be a second, smaller product. We rejected a shared database server: the applications run on SQLite by choice, and putting their monitoring on a server they do not otherwise need inverts the premise of decision 0006. We rejected one database for every application with an application column: every model, query, index and unique constraint would need it, and a missed one mixes applications' data; shards keep the gem's tables and code as they are.

The costs: data leaves each application, SQL values included (`actual_sql` is needed to normalise and fingerprint on the central, which stores it only with its own `capture_actual_sql`), so the central must be run with the trust a database would be. Delivery is at least once, made idempotent per batch by `batch_id`, and held batches live in the sending process's memory, so a long outage or a restart loses data. Settings that shape storage and the dashboard (thresholds, tags, retention, time zone) are the central's, for every application. Features that need the monitored application's own router or tables on the central (route backfill, EXPLAIN) do not work there.
